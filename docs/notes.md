# 設計メモと実測

README から移した細目です。
Jev への聞き方、演出を出す・抑える決まりとその数値、実 API で測った値、まだ確かめていないことを残してあります。
動かし方は [README](../README.md) を見てください。

## しくみ

```
Swift の音声認識 → server.js → SSE → 字幕（発話に id を振る）
  → scheduler（いつ聞くか） → Jev（30 問を 1 リクエスト）
  → director（出すか、抑えるか） → 演出イベント → ステージと音
```

1. `stt/` の Swift CLI がマイクの音を字幕にして、1 行 1 JSON で出す。認識途中の字幕（interim）と確定（final）の 2 種類
2. `server.js` がそれを読み、SSE でブラウザへ流す
3. 字幕を積む。認識途中の字幕には「次の確定が取る id」を付けるので、途中の字幕とその確定は同じ発話として扱える
4. `scheduler` が聞く時を決める。確定は即時。認識途中の字幕は、4 文字以上変わって 600ms たったとき。字幕が 350ms 止まったら、言い切ったとみて確定を待たずに聞く
5. Jev に 30 問をまとめて聞く。Jev は全問を並列に評価するので、問いを増やしても応答時間はほとんど変わらない
6. `director` が答えを演出イベントに変える。しきい値、1 発話 1 回、連発の抑制、ムードの入り抜けはここでコードが決める
7. イベントを、ステージ（映像の合成）と音（SE と声の加工）が受け取って出す。手動のボタンも同じイベントを流す

字幕から演出イベントまでは `src/pipeline.js` にまとめてあり、画面と `sim/live.js` が同じものを通ります。

### 閉集合

出せるものは `src/effects.js` にあります。

- **cue**（瞬発系、15 種と none）：1 つ選ぶと、擬音と画面効果と SE が束で出る。`don` なら「ドン!」と集中線とドンの音
- **mood**（持続系、8 種と none）：1 つ選ぶと、サングラスの色と顔と画面と声の効果が束でかかる。`gloom` なら青いレンズと青ざめ縦線と暗転と雨
- **style**（発話テロップの様式、8 種）：書体と色と動き

レイヤーごとに別々に選ばせてはいません。
Jev は問いを独立に評価するので、レイヤー別に聞くと「ガーン」と笑い声とキラキラのような噛み合わない組が出ます。
束にしておけば、組み合わせの整合は表が保証します。

サングラスは常に掛けていて、ふだんのレンズは黒です。
ムードが入ると、そのムードの色に変わります（`gloom` 青、`cool` 金、`horror` 紫、`panic` 虹色、`rage` 赤、`robot` 緑、`cute` ピンク、`dreamy` 夕焼け）。
ムードは別々の発話 2 つ以上で続いたときだけ入るので、色が変わるのは、ときどきです。

擬音は熱量で 3 段階に変わります（ドン、ドン!、ドドン!!）。
集中線は、熱量が足りるときだけ付きます。

## Jev への聞き方

エンドポイントは `POST https://api.typesafe.ai/v1/systemone`、モデルは `jev-1.13.0` です（[API リファレンス](https://docs.typesafe.ai/api)、[モデル](https://docs.typesafe.ai/models)）。
別名の `jev-latest` は使っていません。
新しい版が出ると黙ってそちらへ切り替わり、`director` のしきい値は 1.13 で測って決めたものだからです。
版を上げるときは `npm run probe` で測り直します。
応答の `usage` にはトークン数しか入っていないので、費用は入力 100 万トークンあたり $0.042（出力は無料）で計算して出しています。
Jev は文章を生成せず、`state` と型付きの問いを受け取って、確率つきの判断を返します。

`state` の中身。

| キー | 内容 |
|---|---|
| `task` | 何をしているかの説明（英語） |
| `transcript.focus` | 判定の対象。話している途中ならその字幕、そうでなければ直前に確定した行（日本語のまま） |
| `transcript.focus_status` | `just finished` / `the speaker paused here, probably finished` / `still being spoken, may be cut off` |
| `transcript.context` | それより前の字幕。直近 30 秒、120 文字まで |
| `delivery` | 話し方の事実。速さと、発話の前の間。本人の中央値と比べた言葉（fast / normal / slow）で渡す |

問いは 30 個です。

| 問い | 型 | 数 |
|---|---|---|
| `cue` どの演出が合うか | choice | 1 |
| `cue_<id>` その演出を、いま出すか | noul | 15 |
| `mood` どのムードが続いているか | choice | 1 |
| `mood_<id>` そのムードが 1 文より長く続いているか | noul | 8 |
| `telop_style` 発話テロップの様式 | choice | 1 |
| `punchline` いまオチを言ったか | noul | 1 |
| `complete` 言い切っているか | noul | 1 |
| `too_thin` 判断材料が乏しいか | noul | 1 |
| `heat` 熱量（deadpan / calm / animated / excited / explosive） | score | 1 |

同じ項目を choice と noul の両方で聞いています。
choice は総和が 1 の相対評価なので、何も合わない場面でも、どれかに寄ります。
noul は絶対評価なので、何も出すべきでない場面では全部が低く出ます。
強さは `choice × min(1, noul / 0.6)` で、noul が低い項目は choice で勝っていても下がります。

判定の対象は 1 つに絞っています。
確定した行と話している途中の字幕を並べて渡すと、前の行のオチを次の発話のものと取り違えます。
オチの直後にふつうの話を続けたとき、次の発話のオチ判定は、1 つに絞ると 0.04、並べて渡すと 0.13 でした。

前回の答えも、直前に出した演出も、Jev には送りません。
送ると自分の答えに引きずられます。
連発を抑えるのは `director` の役目です。

## 出すか、抑えるか

Jev は「いま何が合うか」を答えるだけで、出しすぎも二度出しも気にしません。
それを抑えるのが `src/director.js` です。

瞬発系。

- しきい値は経路ごとに違う。確定 0.35、字幕が止まった 0.45、字幕が伸びている最中 0.6。早い経路ほど字幕が不確かなので厳しくする。ふつうの話の擬音の強さは 0.2 以下で、Jev の票が 2〜3 の擬音に割れた行が 0.3〜0.45 に来る
- 発話テロップは、オチ判定が確定で 0.4、字幕が止まった時点で 0.45 以上のとき。字幕が伸びている最中には出さない。出す文字列そのものが途中になる
- 1 つの発話で出すのは、擬音が 1 回、発話テロップが 1 回。認識途中の字幕で出したら、その確定では出さない。確定が来ないまま 12 文字伸びたら、次の文とみなしてもう一度出してよい
- **言い終えてもまだ何も出していなければ、必ず何か出す。** none を除いた中でいちばんの擬音に根拠があればそれを、無ければその発話をテロップにする。ふつうの話は `plain` の小さめの字幕になる。確定を待つと 3 秒遅れるので、字幕が止まって、言い切ったと Jev が答えた時点でも出す。4 文字に満たない相づちには出さない。`createDirector({ everyUtterance: false })` で切れる
- 判断材料が乏しい確率が 0.7 以上なら、擬音とオチのテロップは出さない
- 応答が 1.5 秒より遅れた答えは使わない。喋りから離れた演出は、無いより悪い
- 擬音の間隔は 1.5 秒、同じ擬音は 8 秒。発話テロップは、前のものが消えてから。演出を出す発話は 20 秒に 12 まで（10 文字前後の短い文で喋っても当たらない高さ。暴走を止める最後の歯止め）
- 擬音もテロップも、出しておくのは 3 秒まで

持続系。

- 答えを指数移動平均でならす。入りのしきい値は 0.55
- 別々の発話 2 つ以上で強く出たときだけ入る。1 つの発話の中で答えが続いても入らない
- **入ってから消えきるまでを 3 秒に収める。** 2.4 秒で切り、画面側のフェードアウトに 0.5 秒ほど。切ったムードは 15 秒入れない。Jev は字幕全体を見てムードを答えるので、悲しい話が終わっても同じムードを答え続け、長く保つと次の話の上にも雨が降る
- ムードを乗り換えるときは、共通のレイヤーに触らない。`gloom` から `horror` へ移っても、暗転は出たまま
- 声の切替は、発話の切れ目まで待つ。声色が言葉の途中で変わると、演出ではなく故障に聞こえる
- 保つ時間は `createDirector()` の `moodMinHoldMs` / `moodMaxHoldMs` で変えられる。レイヤーごとの最長は `layerMaxHoldMs`（例: `{ screen: 8000 }`）

熱量は `dress()` で見た目と音の量に写します。
テロップの大きさ、画面の揺れ、SE の音量、集中線の本数、表示時間です。

## 検証

```sh
npm test                 # node:test。判断の層と、座標や包絡を決める関数
npm run probe            # 実 API。聞き方の下調べ（none / interim / heat / style）
node sim/probe.js burst  # 実 API。1 秒に 2 回を 15 秒。ほかに state / facts
npm run sim -- --save logs/live.jsonl   # 実 API。台本を実時間で流して、演出イベントまで通す
npm run sim -- --script promo --pace 6.5 --gap 600   # 実 API。宣伝用の 1 分の話を、人が喋る速さで通す
npm run sweep logs/live.jsonl           # 録った答えを director に流し直して、しきい値を試す。API は呼ばない
node sim/replay.js logs/live.jsonl      # 録った答えを、いまの director に流し直して、行ごとに何が出るかを見る。API は呼ばない
```

`src/` のうち、DOM と WebAudio に触れるのは `main.js`、`media.js`、`stage/` の描画、`audio/` の再生だけです。
判断の層と、図形や動きや音の数値を決める関数は、Node からそのままテストできます。

実測（2026-09-19、Apple M5、`jev-1.13`）。
応答時間と費用は TypeSafe の API で測り直した値、判断の中身は OpenRouter 経由（`typesafe/jev-1.13`）で測った値です。
同じ発話を両方に送って、答えが同じになることは確かめました（`bishi` 0.99、オチ 0.84、熱量 0.60）。

| 項目 | 結果 |
|---|---|
| 応答時間 | 中央値 250 ms、最小 200、最大 605（30 問を 1 リクエスト、12 回。最初の 2 回は接続の確立ぶん遅い）。OpenRouter 経由では中央値 266〜282 ms だった |
| 費用 | 1 回 約 $0.00011（入力 2,700 トークン）。台本を流した 47 秒で 54 回、$0.0063。この調子で 1 時間なら $0.48 |
| ふつうの話（8 行） | すべて none が勝った。0.5 以上で誤って出る行は 0 |
| 台本（12 行）を確定として聞く | 期待した演出が上位 3 つに入ったのは 10/10。強さは 0.59〜1.00 |
| 台本を実時間で流す | 期待した演出 7/8、何も出してほしくない行での誤発火 0 |
| 言い切ってから演出まで | 中央値 684 ms、最小 554、最大 771（偽の音声認識で。下の注を参照） |
| オチ判定 | ふつうの話と相づちは 0.05 以下。オチの行は 0.52〜0.88 |
| 言い切り判定 | 言い切った文は 0.83〜0.93、「えーっと、それで、あのー」は 0.33 |
| 熱量 | 「まあ、いいんじゃない」0.23 から「うおおおおやばいやばいやばい！！」1.00 まで、5 段階の文で順に上がった |
| 発話テロップの様式 | 6/6（ツッコミ、自虐、ホラー、かわいい、ふつう、決め台詞） |
| 顔の検出 | 1 回 12〜24 ms（`@mediapipe/tasks-vision` 1.0.1、GPU）。0.10.21 と比べて 1.0.1 のほうが少し速かった |
| ピッチシフタ | 220 Hz を 1.5 倍で 331 Hz、0.7 倍で 153 Hz。遅れは窓の半分で約 22 ms |
| 音の出力の遅れ | 29 ms（`AudioContext` の報告値） |

実時間で外した 1 行は「うおおお完成した！」で、答えは `kiran` 0.70 でしたが、4 秒前にキラーンを出していたので抑えました。
この表は、しきい値を下げて「言い終えたら必ず何か出す」ようにする前の値です。いまの設定では、ふつうの話の行にも `plain` のテロップが出ます。

下調べで分かったこと。

- オチかどうかは、フリがあって決まる。文脈なしで聞くと、夢オチの「…っていう夢を見たんですよ」は 0.13〜0.20。それまでの話を渡すと 0.52〜0.56
- 文脈を渡していれば、字幕が止まった時点のオチ判定は、確定時とほぼ同じ値になる（0.75 と 0.75、0.88 と 0.87）。確定を待たずにテロップを出してよい根拠
- 言い切る前は none が勝ち、判断材料の乏しさが 0.7 以上になる。「いやなんでやねん、」まで来ると `bishi` が 0.90 になり、言い切る前に出せる
- `probabilities` は、score では段階の番号をキーにしたオブジェクトで返る

画面で確かめたこと。
カメラの代わりに顔写真を流し、手動のボタンで出した。

- 擬音、集中線、青ざめ縦線、キラキラ、発話テロップ、暗転、雨、グリッチ、走査線、波打ち
- サングラスが目の位置に、顔の大きさと傾きに合って載る。左右を反転していても合う。何も押さなくても掛かっていて、レンズの色は青にも虹色にも変わる
- 集中線は顔へ向かい、擬音は顔を避けて置かれる
- 発話テロップは画面の下 3 分の 1 に収まり、文節の切れ目で折れる
- `?stage=1` でステージだけが画面いっぱいに出る

音で確かめたこと。
マイクの代わりに 220 Hz の正弦波を流して、数値で見た。

- 15 種の SE を熱量 3 段階で合成して、例外も NaN も出ない
- 声の出力を閉じていると、出力は無音。開けると素通しの音量で出る
- 声色は後から入れたものが勝ち、切ると前のものに戻る。60 回続けて切り替えても例外は出ない

まだ確かめていないこと。

- 音を耳で聞いていない。SE の音量は数値でそろえただけで、声の加工が人の声でどう聞こえるかも分からない。2 タップ方式のピッチシフタは、周波数によって音量が 3 dB ほど揺れる
- 実際のカメラとマイク。暗い部屋や横顔での顔の追跡、カメラを映した状態での描画の速さ
- 実際の音声認識での遅れ。上の 684 ms は、言い切ってから 450 ms で確定が届く偽の音声認識での値。Apple の音声認識は、言い終わってから確定を返すまでに 2.9 秒かかった（1 回だけの観測）。認識途中の字幕はまとまって届き、まとまりの間は最大 1 秒ほど空く。このため演出は、確定ではなく「字幕が止まった」時点で出すのが主になる。続けて喋ったときに字幕がどこで切れるかは、まだ見ていない
- Swift の音声認識と Chrome は、同時に同じマイクを開ける（確かめた）。録画用の音の出口に、内蔵マイクの音が届くところまでも確かめた。保存した動画で声が聞こえるかは、まだ確かめていない
- 録画のうち、ウィンドウとタブを録る流れ（ブラウザの選択画面を人が操作する）と、保存した動画の再生。確かめたのは、この Chrome が映像と音を mp4 で録れることと、「ステージだけ」で録画が例外なく始まることまで
- OBS への取り込み。Chrome は隠れたウィンドウの描画を止めるので、OBS の後ろに隠さない運用が要る
- 長く喋り続けたときの費用と、相づちの多い会話での誤発火

## 録画

ステージの下の「● 録画」（または `R` キー）で、映像と音を 1 本の動画にして保存します。
止めると `jev-live-20260919-101530.mp4` の名前でダウンロードされます（mp4 で録れないブラウザでは webm）。

映す範囲は 3 通りです。

| 範囲 | 映るもの | 取り方 |
|---|---|---|
| ウィンドウ（既定） | ブラウザの枠、パネル、ステージ | ブラウザの画面共有。選択画面で、この Chrome のウィンドウを選ぶ |
| このタブ | パネルとステージ | ブラウザの画面共有。選択画面で、このタブを選ぶ |
| ステージだけ | ステージ（1280x720、`?scale=1.5` なら 1080p） | キャンバスをそのまま録る。選択画面は出ない |

音は、画面共有からは取りません。
macOS の Chrome は、ウィンドウの共有では音を渡してくれないためです。
代わりに、アプリの中で効果音と声を混ぜたものを録画に入れます。
スピーカーへの出力とは別の出口なので、「加工した声を出力する」を閉じたままでも、声は録画に入ります。

- 効果音は、音量のスライダーを通ったあとの、聞こえているとおりの大きさで入る
- 声は 3 通り。声色の効果つき（既定。効果が掛かっていないあいだは素通しなので、ふだんは生の声と同じ）、生のマイク、声なし
- 初めてウィンドウかタブを録るときは、macOS の「システム設定 > プライバシーとセキュリティ > 画面収録」で Chrome を許可する
- スピーカーで鳴らすと、マイクが効果音を拾って二重に入る。ヘッドホンを使う
- ブラウザの「共有を停止」を押しても、そこまでが保存される

## マイク

マイクは 2 か所で別々に開いています。
音声認識（Swift）は macOS の既定の入力を、声の加工と録画（Chrome）は Chrome が開いたマイクを使います。

Chrome にデバイスを指定せずにマイクを頼むと、macOS の既定ではなく、一覧の先頭のデバイスを開くことがあります。
Background Music や BlackHole のような、Mac の音を引き回すための仮想の入力が先頭にあると、エラーにならないまま完全な無音が届きます。
字幕は出るのに、声の加工も録画の声も無音、という状態になります（この Mac で実際に起きた）。

そこで、マイクは macOS の既定の入力を名指しで開きます（Chrome では `default` という id）。
「できれば既定を」（`ideal`）という頼み方は Chrome に無視されたので、必須（`exact`）で頼んでいます。
名指しが通らなければ指定なしで開き、それが仮想の入力なら実マイクに開き直します。

- パネルの「音」でマイクを選べる。選んだものは覚える。仮想の入力には、そう書き添える
- マイクから完全な無音（値がちょうど 0）が 3 秒続いたら、見出しの横の状態が赤い「無音」になる。本物のマイクは、黙っていても環境音で 0 にはならない

## 音とハウリング

加工した声の出力は、既定で閉じています。
スピーカーで出すとマイクに回り込み、ハウリングします。
パネルの「加工した声を出力する」で開けます。
この設定は保存しません。
次に開いたとき、スピーカーのままいきなり鳴るのを防ぐためです。

SE は既定で鳴ります。
スピーカーで鳴らすと音声認識が拾うことがあるので、ヘッドホンを使ってください。

OBS での構成は 2 通りです。

| | 声はそのまま | 加工した声を配信に載せる |
|---|---|---|
| OBS のマイク入力 | 使う | 外す |
| OBS のアプリ音声キャプチャ | SE だけが載る | 加工した声と SE が載る |
| 「加工した声を出力する」 | 閉じる | 開ける |
| ヘッドホン | 推奨 | 必須 |

SE は WebAudio で合成しています。
`assets/se/<id>.mp3` を置くと、そちらを優先します（`don.mp3`、`laugh.mp3`、`laugh-2.mp3` のように。複数あれば毎回どれかを選ぶ）。
笑い声は合成では質が出ないので、素材を置くことを勧めます。
このディレクトリは git に入れません。

## 音声認識

`stt/` は、マイクの音を日本語の字幕にする Swift の CLI です。
[リアルタイム脳内メーカー](https://github.com/ponyo877/jev-realtime-brain-scanner)のものをそのまま使っています。
Whisper 系を採らなかった理由も同じで、無音のあいだに文を作り出すことがあるためです。
ここでは字幕がそのまま Jev の入力になるので、黙っているだけで演出が出てしまいます。

認識エンジンを替えるときは、同じ形の JSONL を stdout に出すコマンドを `STT_CMD` に指定します。
